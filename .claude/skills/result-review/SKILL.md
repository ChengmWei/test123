# 結果檢討

> 這是**挖空模板**。標 ★ 的地方要你自己填。
> 重點是「看到什麼現象 → 代表什麼問題 → 下一次怎麼改」，讓 AI 像店長一樣檢討。

## 什麼時候用

每跑完一次 `npm run simulate`，要決定下一版策略怎麼改時。

## 試算結果裡有哪些線索

試算工具每天會印出：客人數、收入、備貨、宣傳、報廢（清潔費）、淨利、任務、星等、資金，以及「沒買到的客人」：

| 線索 | 意思 |
|---|---|
| 賣完買不到 | 有人想買，但貨不夠 |
| 嫌太貴 | 價格超過客人剩下的預算 |
| 想吃的沒上架 | 客人想吃的菜今天沒賣 |
| 因為討厭的菜不進門 | 上架了某位客人討厭的菜 |

## 對症下藥表

| 看到的現象 | 代表的問題 | 下一次怎麼改 |
|---|---|---|
| 賣完買不到很多 | 備貨太少 | 那樣菜多備一些（注意合計不能超過 80 份） |
| 報廢 15 份以上 | ★ **實際觀察：** 當天 `waste` 合計至少 15，並看 `wasteFee`。<br>**可能原因（推測）：** 備貨高於需求，或客人因太貴、沒上架、討厭的菜而沒有購買。 | ★ 先驗算每樣菜 `waste = stocked − sold`，再用 `reorder-check` 調整報廢過多的菜。若同一天也有太貴或不進門，先比較原因，不要只減量。 |
| 嫌太貴很多 | ★ **實際觀察：** `tooExpensive` 人數偏高。<br>**可能原因（推測）：** 客人第一個沒買成的菜價格超過預算，定價可能高於這群客人可接受的範圍。 | ★ 核對客人預算與定價，再依 `pricing-rules` 心法 1 測試降價，並列出降價前後的單份毛利。 |
| 想吃的沒上架很多 | ★ **實際觀察：** `notOnMenu` 人數偏高。<br>**可能原因（推測）：** 當天菜單沒有涵蓋這群客人的需求，或最多 4 樣的限制排擠了這道菜。 | ★ 找出客人想吃的菜，比較替換後的需求、毛利和報廢風險。上架前先確認不會讓其他客人因討厭而不進門。 |
| 因為討厭的菜不進門 | ★ **實際觀察：** `hatedOnMenu` 大於 0，這些客人不進門、不留評價。<br>**可能原因（推測）：** 上架的某道菜正好是這群客人的 `hates`。 | ★ 比較保留這道菜的收入，以及下架後這群客人可能帶來的收入，再決定是否替換。 |
| 星等往下掉 | ★ **實際觀察：** `stars` 下降；用滿意 ÷ 進店人數、不滿 ÷ 進店人數，對照規則書門檻。<br>**可能原因（推測）：** 不滿來自賣完、太貴或沒上架，或售價高於建議售價使滿意人數減少。 | ★ 先處理占比最高的不滿原因；若是高價造成滿意下降，測試回到建議售價。比較隔天來客數，確認星等變化的影響。 |
| ★ 我自己發現的現象：宣傳後增加來客，但淨利未改善 | ★ **實際觀察：** 與同一天未宣傳的版本相比，客人數增加，但 `profit` 沒有增加。<br>**先核對：** 淨利變化 ＝ 新增收入 − 新增備貨成本 − 新增清潔費 − 新增宣傳費。<br>**可能原因（推測）：** 新增客人沒買到、買的是低毛利品項、多備貨造成報廢，或新增毛利低於宣傳費。 | ★ 核對算式後才調整：貨不夠就先補貨；報廢增加就調整備貨；新增毛利仍低於宣傳費，就降低或取消宣傳。下一版盡量只改宣傳這一項來比較。 |

## 步驟

1. 讀試算結果，逐天找出上表的現象
2. 每一個現象，照對症下藥表提出一個修改
3. **一次最多改 3 個地方**，這樣才知道是哪個修改有效
4. 把修改後的策略存成新的檔案（例如 `plans/v2.json`），不要覆蓋舊的，方便比較

## 回報格式

```text
這一版的結果：最終資金 …、星等 …、報廢 …
發現的問題：
1. 第 N 天：（現象）→（問題）
修改：
1. …
下一版檔名：
```

## 不准做的事

- 不准修改遊戲檔案（`src/` 底下的任何檔案、客人包）
- 只能新增或修改 `web-lab/plans/` 裡的策略檔
