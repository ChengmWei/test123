# 補貨檢查

> 這是**挖空模板**。標 ★ 的地方要你自己填。
> 重點是「數字一定要從盤點資料抄，不能自己編」，而且每個數字都要能驗算。

## 什麼時候用

- 跑完 `npm run simulate`，要決定下一版策略每樣菜備幾份時
- 在瀏覽器玩完一天，想看「倉庫盤點」頁的結果該怎麼調整時

## 資料從哪裡來

在 `web-lab` 資料夾執行：

```text
npm run simulate -- plans/策略檔.json --json
```

每一天的 `inventory` 欄位，是那天每樣上架的菜的盤點：

| 欄位 | 意思 | 怎麼驗算 |
|---|---|---|
| `name` | 菜名 | — |
| `stocked` | 早上備了幾份 | 策略檔裡的 `qty` |
| `sold` | 賣出幾份 | 打烊報表 |
| `waste` | 報廢幾份 | 備貨 − 賣出 |
| `missed` | 賣完之後，還有幾位客人想買卻沒買到 | 客人卡片上「賣完了」的數量 |
| `status` | `ok` 正常、`out` 缺貨、`over` 報廢過多 | 規則書「倉庫盤點」 |
| `suggest` | 明天建議備幾份 | 賣出 ＋ 沒買到 |

## 步驟

1. 執行上面的指令，讀每一天的 `inventory`
2. 先驗算：`waste` 有沒有等於 `stocked − sold`？對不上就停下來回報，**不要用錯的資料做建議**
3. 挑出 `status` 不是 `ok` 的菜
4. ★ 建議備貨量要不要再調整（例如：明天客人比較多的日子，要不要多備幾份？多備幾份？）：不自動加減。
   - 原始數字只能來自使用者提供的盤點資料，或本 Skill 列出的資料來源；計算出的數字都要列出算式。
   - 只調整 `status` 是 `out` 或 `over` 的菜，基礎建議量依規則書計算：賣出 ＋ 賣完後沒買到，例如 `5 + 5 = 10`。
   - `status` 是 `ok` 的菜不提出調整，下一版沿用原本的 `stocked`。
   - 客人可能變多的日子只能文字提醒，不可自行加成。
   - 試算資料的建議對應下一版的同一天；瀏覽器單日盤點的建議對應明天。
5. ★ 同一樣菜連續幾天都缺貨或報廢過多，要怎麼提醒：連續 2 天以上是同一種狀態時，在該菜後面標「連續缺貨 N 天（第 a～b 天）」或「連續報廢過多 N 天（第 a～b 天）」。這只是提醒，不改變建議量的算法。
6. 用下面的回報格式回報

## 回報格式

```text
策略檔：
驗算結果：通過 / 第 N 天的 ○○ 對不上（寫出哪個數字）
第 N 天：
  缺貨：菜名 備 … 賣 … 沒買到 … → 建議 …
  報廢過多：菜名 備 … 賣 … 報廢 … → 建議 …
★ 我想多看一個欄位：建議備貨成本（單份成本取自 docs/RULES.md「菜單」）
  菜名 建議份數 … × 單份成本 … = … 元
  當日合計：… + … = … 元
下一版每天建議的備貨量：
```

## 寫完檢查

- [ ] 每一個數字都能在盤點資料裡找到
- [ ] ★ 我再加一條檢查：`status` 符合規則書、`suggest` 等於 `sold + missed`、單份成本與規則書相同、每個計算結果都有算式，且下一版每天合計不超過 80 份。任一項不符合就停下來回報。

## 不准做的事

- 不准修改任何檔案（這個 Skill 只讀不寫，要改策略交給 result-review）
- 不准自己編數字，或用「大概」、「差不多」帶過
- ★ 我再加一條：不准調整狀態正常的菜，也不准把天氣、事件、星等、宣傳或個人經驗自行換算成加減份數。
